# Python Core Training

Практика по декораторам, GIL, потокам, asyncio и контекстным менеджерам.
Условия и критерии проверки находятся в [Issues](https://github.com/sraduhin/Python-Core-Training/issues).
На каждую тему — одна лёгкая и две сложных задачи.

## Как сдавать задачи

1. Выбери issue. Для каждой задачи создай отдельную ветку от актуального `main`.
   Имя ветки указано в условии. Не складывай несколько решений в одну ветку.
2. Положи решение, тесты и ответы на вопросы в каталог `tasks/<slug>/`, указанный в issue.
   Для экспериментов добавь туда скрипт запуска и отчёт с условиями измерения.
3. Открой отдельный PR в `main`. В описании укажи `Closes #<номер issue>`,
   команду запуска тестов и короткое объяснение выбранного подхода.
4. Запроси ревью у `Khachatur86`. После замечаний продолжай работать в той же ветке.
   Следующую задачу начинай в новой ветке от обновлённого `main`.

Пример создания ветки:

```bash
git switch main
git pull --ff-only origin main
git switch -c task-01-example
```

## Среда и проверки

Используй Python 3.13. Задачи про GIL рассчитаны на обычную сборку CPython с включённым GIL.
Внешние сервисы, базы данных и реальные сетевые запросы не нужны.
Для проверки достаточно стандартной библиотеки (`unittest`, `unittest.IsolatedAsyncioTestCase`);
при желании можно использовать `pytest`.

Пример запуска тестов одной задачи на стандартной библиотеке:

```bash
python3.13 -m unittest discover -s tasks/<slug> -p 'test_*.py' -v
```

Если используешь другой способ запуска, запиши точную команду в PR.
Синхронизируй конкурентные проверки через `Event`, `Barrier` и другие подходящие примитивы.
Таймауты могут страховать тест от зависания; фиксированные задержки не должны определять его успех.
В экспериментах с производительностью не нужно добиваться заранее заданного ускорения:
важны воспроизводимые измерения и объяснение результата.

Оценки в SP показывают относительную сложность задачи и не переводятся в дни.
