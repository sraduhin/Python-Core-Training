# GIL: CPU-нагрузка против ожидания

Модуль `gil_compare.py` с функцией `compare(kind, ...)` прогоняет одну и ту же
последовательность заданий последовательно и в `ThreadPoolExecutor`, собирая
полные длительности каждого запуска через `perf_counter()`.

## Запуск

Тесты:

```bash
python3.13 -m pytest tasks/gil-cpu-vs-wait -q
```

Эксперимент (печатает медианные длительности и отношение threads/seq):

```bash
cd tasks/gil-cpu-vs-wait && python3.13 main.py
```

## Наблюдения

Пример одного прогона на CPython 3.13 с включённым GIL (`gil_enabled=True`),
`jobs=4`, `workers=2`, `repeats=5`:

| kind | sequential (median) | threads (median) | threads/seq |
|------|---------------------|------------------|-------------|
| cpu  | 0.0264s             | 0.0261s          | ~0.99       |
| wait | 0.0953s             | 0.0495s          | ~0.52       |

- **CPU (`j + sum((i*i) % 97 ...)`)** — чистый Python-цикл держит GIL, поэтому
  потоки не исполняются по-настоящему параллельно и лишь сменяют друг друга.
  Отношение около 1: ускорения нет, а накладные расходы на создание/закрытие
  пула и переключение потоков могут даже слегка замедлить.
- **wait (`time.sleep(delay)`)** — `sleep` отпускает GIL, пока поток ждёт,
  поэтому `workers` ожиданий перекрываются. При 2 воркерах и 4 заданиях время
  падает примерно вдвое (~0.52).

Конкретные числа шумят от запуска к запуску: их определяют стоимость старта
пула, планировщик ОС, прогрев и фоновые процессы. Поэтому в тестах не
проверяется отношение длительностей — только контракт (одинаковые
упорядоченные результаты, ровно `repeats` конечных неотрицательных измерений,
корректная валидация и отсутствие «утёкших» потоков). Для наблюдения за
эффектом смотрим медиану нескольких повторов, а не одно измерение.
